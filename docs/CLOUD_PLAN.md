# Cloud-first production plan (free or trial tiers; local Spark only when unavoidable)

Principle (Commander, 2026-10-17): do everything in the cloud on free or trial tiers so nothing waits on a local machine. Use the
Spark node only for work that truly needs local compute (AI image or video rendering). Fast and cheap beats elegant.

## What I changed this pass to make that work
1. **Ratings moved into Postgres.** They are computed when a game becomes final, in the same transaction. There is no worker to host and no
   scheduler to pay for. My earlier "run the worker every 10 minutes" workflow would have used about 4,300 billed minutes a month against a
   2,000-minute allowance. A new guard now fails the build if any workflow runs more than hourly.
   The SQL port is checked against the TypeScript: 9,058 Plackett-Luce player updates (1v1 to 5v5) agree to 7e-15, plus 6,000 Elo,
   repeat-weight and display checks. A rating bug can never block a game from finalizing (it records the error and a retry job fixes it).
2. **Scheduling inside the database.** `pg_cron` (expire stale games every 15 minutes, retry failed rating jobs every 30). Conditional, so it
   is simply skipped on plain Postgres. Untested here because pg_cron is not installed in this sandbox.
3. **Installable web app.** Manifest, icons, SPA fallback (`_redirects`), cache and security headers, `geolocation=(self)` only.
4. **Generated assets**: `pnpm assets` (icon, adaptive icon, splash, favicon, PWA icons) and `node scripts/make-screenshots.mjs`
   (App Store 1290x2796 and Play 1080x1920). A test pins sizes, opacity and that `app.json` points at real files.
5. **Gated workflows** (they do nothing until you add the secrets): `deploy-web`, `supabase` (push migrations + weekly keep-alive so the free
   project does not pause), `eas-build` (manual), `store-assets` (manual, uploads screenshots as an artifact).
6. **CI is now verified online.** It had been running on every push; reading its logs found a real bug (my secret guard tripped on its own test
   fixture) and confirmed the `database` job works on a real GitHub runner.

## Fastest path to real users (about 30 minutes of your time, all free)
Only you can create accounts. In this order:
1. **Supabase**: create a free project. Add repo secrets `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD` and variables `SUPABASE_PROJECT_REF`,
   `SUPABASE_URL`, `SUPABASE_ANON_KEY` (the anon key is public by design; never put the service-role key in GitHub variables). Run the
   `supabase` workflow once. Then load the courts: `pnpm courts:import` and run the generated SQL in the dashboard SQL editor.
2. **Cloudflare**: create a Pages project (Direct Upload). Add secrets `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` and variables
   `CF_PAGES_PROJECT`, `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`. Merge to `main` and the app is live at a `*.pages.dev` URL
   that testers open on any phone and "Add to Home Screen".
3. **Expo** (optional, for Android testers): create an account and a token (`EXPO_TOKEN`); run `eas-build` with profile `preview` for an installable APK.
4. **Later, not free**: Google Play (one-time fee, about $25 per the earlier audit), Apple Developer Program (annual fee, about $99; verify).
   The PWA avoids both while you learn what players want.

## What genuinely needs the Spark node (local GPU)
Only AI-generated art and video: hero illustrations, a promo clip, stylised avatars beyond the code-drawn ones. Everything else above runs in
the cloud. I will not queue anything on the shared GPU without your OK. If you would rather stay 100% cloud, a free image API can do hero art
too; say so and I will compare options.

## Risks to watch
- **Supabase pauses a free project after a week without activity.** The weekly keep-alive covers it once you set the secrets; it is also
  a reason to move to Pro before a public launch.
- **Free tiers change.** Numbers above came from search results of the official pages (I could not open them directly from this sandbox): re-check before relying on them.
- **EAS queues** can be slow on the free plan; only build when you need an installable file.
- **PWA limits**: no background location (we do not use it), and push notifications on iOS only work for an installed app (reported, not verified here).
- Cloudflare Pages bandwidth is "unlimited" only according to third parties.

## Never in the repo
No keys, tokens or service-role credentials. They live in GitHub secrets. A guard fails the build if something that looks like a key is committed.

## Web app (PWA) first, or the stores? (Commander asked 2026-10-17)

| | PWA first | Stores first |
|---|---|---|
| Cost | $0 (Cloudflare Pages free) | Play about $25 once, Apple about $99/year (verify) |
| Speed | Every merge can go live in minutes | Review takes days; Play needs 12 testers for 14 days before production |
| Testers | Send a link; works on any phone | Testers need store accounts/invites |
| Feedback loop | Fix and redeploy instantly | Each fix is a new build and review |
| Location | Foreground GPS works in the browser (asks permission) | Same, plus better reliability |
| Weak spots | No App Store presence; iOS push only for installed apps; less "real app" feel; browsers can evict storage | Heavier process; wrong first impressions are costly |
| Risk | Low: private link, easy to pull | Higher: public review of an unpolished app |

**Recommendation: PWA first, stores after the design pass.** It matches "free tier, no bottlenecks", lets you and a small circle try real games at a real court, and the same code ships to the stores later (Expo). Start the Play 14-day tester clock only once the design is approved, since that clock cannot be rushed.

## Scoring modes
- **Live**: every point is confirmed by both sides as it happens. Most trusted, a few more taps. This is the default.
- **Quick**: play normally, then one confirmation of the final score at the end. Faster, easier to dispute afterward. Kept as an option.
